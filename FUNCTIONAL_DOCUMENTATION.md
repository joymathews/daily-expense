# Functional Documentation

## Application Platform [FUNC-CORE]

### User Interface [FUNC-UI]
- [FUNC-SKEL-UI-1] The user must be able to access the application dashboard through a secure web browser session.
- [FUNC-SKEL-UI-2] The user must see a personalized greeting and "DAILY EXPENSE" branding on the dashboard to confirm operational status.
- [FUNC-SKEL-UI-3] The user must experience a high-density responsive interface optimized for desktop, tablet, and mobile screens.

### Direct Ledger Ingress
- [FUNC-CORE-2] Direct Transaction Entry: The user must be able to directly log complete transaction records (merchant, amount, currency, transaction date, category, payment method, and optional notes) into the Gold ledger from the Data Ingestion page. Direct entries skip the Bronze and Silver layers, stay on the same entry form upon submission (clearing fields to allow consecutive entries), and are visually identifiable later in the ledger as direct manual entries with the source type labeled as "Manual".

### System Operations [FUNC-SYS]
- [FUNC-SKEL-SYS-1] An external monitoring system must be able to verify the health of the application services to ensure maximum uptime.
- [FUNC-SYS-2] System Logging Configuration: The user/maintainer must be able to configure the active logging level (trace, debug, info, warn, error, fatal, silent) and specify the log file destination via standard server environment variables (`LOG_LEVEL` and `LOG_FILE_PATH`).
- [FUNC-SYS-3] Backend HTTP Logging: The system must automatically record details of all incoming API requests (HTTP method, path, response status code, and latency) and print them to standard output or log files.
- [FUNC-SYS-4] Frontend Error Logging Ingestion: The system must support a dedicated `/api/logs` API endpoint that receives, validates, and logs client-side logs sent from the frontend application, marking their metadata source as `frontend`.
- [FUNC-SYS-5] Consolidated Log Persistence: The system must support writing both backend and frontend logs to the same central log file to provide a single, unified timeline of events for auditing and troubleshooting.
- [FUNC-SYS-6] Open Source Log Viewer Integration: The maintainers must be able to use standard open-source log tools (specifically `pino-pretty` for the terminal and `Logdy` for local web-based filtering) to parse, view, and search the consolidated JSON logs.

## User Authentication [FUNC-AUTH]
- [FUNC-AUTH-1] The user must be challenged for credentials (username/email and password) before being allowed to access protected system areas.
- [FUNC-AUTH-2] The system must remain inaccessible to unauthenticated users, enforcing a redirection to a secure login interface.
- [FUNC-AUTH-3] Authenticated users must have the ability to securely terminate their session (Log Out).
- [FUNC-AUTH-4] The system must isolate transaction data (raw inputs/Bronze, staging transactions/Silver, and confirmed ledger/Gold) by user. A logged-in user must only be able to view, save, modify, and delete their own transaction records. Other users' records must not be visible or modifiable under any circumstances.

## Data Ingestion & Medallion Pipeline [FUNC-GMAIL]
- [FUNC-GMAIL-1] Navigation: The user must be able to navigate to the Data Ingestion page (`/ingestion`) and the Transaction Pipeline page (`/pipeline`) through the primary navigation menu.
- [FUNC-GMAIL-2] Configuration: On the Data Ingestion page (Gmail tab), the user must be able to define granular filters to target specific receipt emails. At least one Sender Email and a Date Range (start and end date) are mandatory. The Subject filter is optional.
- [FUNC-GMAIL-3] Gmail Authentication: The user must be prompted to authorize the system to access their Google account via a secure OAuth2 popup under the Gmail tab of the Data Ingestion page.
- [FUNC-GMAIL-4] Display: The user must be able to scan their staging review queue (Silver layer) and verified ledger (Gold layer) chronologically in high-density tables displaying the transaction date first. To maximize table density and focus the user's attention, Category and Method must be displayed in separate columns, the Notes column must be excluded from the lists, and the tables must not display row action buttons (such as Review, Correct, or Delete); instead, the user must be able to click on primary textual identifiers (Title in Bronze, Merchant in Silver/Gold) to open the details or correction modals.
- [FUNC-GMAIL-5] Pagination: The system must retrieve all matching emails for the specified filters by automatically paginating through the Gmail API results.
- [FUNC-GMAIL-6] Input Segregation: The system must automatically analyze fetched raw inputs and categorize them into two lists: "with transaction" and "without transaction" based on transactional keywords in the title or content snippet.
- [FUNC-GMAIL-7] Separate Presentation: The system must display the two lists of raw inputs (transactional and non-transactional) in separate sections or tabs to the user in the Bronze layer.
- [FUNC-GMAIL-8] Manual Review: The system must allow the user to manually review raw inputs and move them between the "with transaction" and "without transaction" sections via the details modal, keeping the main table views uncluttered.
- [FUNC-GMAIL-9] Raw Input Detail View: The user must be able to click on the title field of a fetched raw input in the Bronze table to view its details (sender, title, date, source type, and full decoded plain-text body content) in a secure modal popup.
- [FUNC-GMAIL-10] Modal Action Override: Inside the detail modal view, the user must have the option to mark the raw input as transactional or non-transactional, which updates the local state and count badge immediately.
- [FUNC-GMAIL-11] Local Ingestion Logging & Audit Trail: The system must automatically store a complete local copy of the fetched raw input history so that the application has a reliable, queryable log of raw messages for auditing and re-processing.
- [FUNC-GMAIL-12] Staging Review Queue: The system must automatically scan raw inputs and extract transaction-related fields (such as merchant, amount, currency, and date) into a staging review queue so the user can verify them before they affect reports.
- [FUNC-GMAIL-13] Review and Final Ledger Approval: The user must be able to edit, correct, and approve transactions from the staging review queue, clicking on the Merchant field in the Silver table to open the review modal and confirm their accuracy before they are finalized as core expense records.
- [FUNC-GMAIL-14] Automatic Duplicate Ingestion Prevention: The system must detect and skip previously processed raw inputs during successive fetches, ensuring the user is never prompted to review or log the same input multiple times.
- [FUNC-GMAIL-15] Separate Data View Options: The user must be able to view separate lists of their data matching the Medallion layers: Raw Inputs (Bronze), Extracted Staging (Silver), and Confirmed Ledger (Gold).
- [FUNC-GMAIL-16] Date Range Filtering: The user must be able to filter the listed records in all Medallion tables (Bronze raw inputs, Silver staging pending, and Gold confirmed ledger) by selecting a start and end date range. The date range filter controls must be rendered contextually in the active view of all three tabs, allowing the user to filter table data dynamically at any stage of the pipeline.
- [FUNC-GMAIL-17] On-Demand Ingestion & Batch Extraction: The user must be able to trigger the Ollama extraction logic manually for a single raw input (from both the checkboxes in the table view and directly within the details modal, provided the raw input is marked as a transaction) or in batches for multiple selected raw inputs.
- [FUNC-GMAIL-18] Confirmed Ledger Corrections: The user must be able to edit and save corrections directly to confirmed transaction records, clicking on the Merchant field in the Gold table to open the corrections modal and confirm their changes.
- [FUNC-GMAIL-19] Raw Input Deduplication: The system must verify that duplicate raw input imports are ignored at the database level using a unique source reference (e.g. Gmail Message ID) as a unique primary key.
- [FUNC-GMAIL-20] Data Lineage Tracing: The system must display lineage linkages between Bronze, Silver, and Gold records, allowing the user to view original source content from staging or ledger items.
- [FUNC-GMAIL-21] Processed Inputs Visibility: Processed raw inputs are completely hidden from the Bronze list view (retaining them in the database for lineage tracing) to prevent duplicate ingestion or extraction attempts and keep the workspace clutter-free.
- [FUNC-GMAIL-22] Silver Batch Approval: The user must be able to select multiple staging transactions in the Silver queue and approve them in a single batch operation, promoting them directly to the Gold ledger.
- [FUNC-GMAIL-23] Bronze Ingestion Status Filter: The user must be able to filter the Raw Inputs (Bronze) list based on their status (e.g., show "All", "Unprocessed", or "Rejected"). Processed raw inputs are completely hidden.
- [FUNC-GMAIL-24] Payment Method Extraction: The user must be able to see how a transaction was made (such as UPI, credit card, bank transaction) automatically extracted from raw inputs and displayed in the staging review queue (Silver layer).
- [FUNC-GMAIL-25] Staging Payment Review & Editing: The user must be able to view, edit, and correct the extracted payment method in the staging queue (Silver layer) before promoting it to the final ledger.
- [FUNC-GMAIL-26] Verified Ledger Method Display & Correction: The user must be able to view the payment method in the ledger tables and edit or correct the payment method of approved transaction ledger records in the Gold table.
- [FUNC-GMAIL-27] Ingestion Progress Tracking: On the Data Ingestion page (Gmail tab), the user must be informed immediately when the fetching process has started, see real-time progress updates, and receive a clear confirmation message upon completion.
- [FUNC-GMAIL-28] Extraction Progress Tracking: The user must be informed immediately when the raw input extraction process (on-demand for a single raw input or in batch) starts, see real-time progress updates, and receive a clear confirmation message upon completion.
- [FUNC-GMAIL-29] Ingestion Filter Layout Isolation: The fetching configuration filter panel ('Fetcher Config') must only be displayed on the Data Ingestion page, and must be hidden on the Transaction Pipeline page.
- [FUNC-GMAIL-30] Cross-Stage Medallion Lineage Explorer: When viewing any record (Bronze, Silver, or Gold) in the detail view modal, the system must dynamically trace and display the status and details of corresponding records in the other two stages of the Medallion pipeline (e.g. Bronze raw input details, Silver staging details, and Gold confirmed ledger details), establishing absolute data lineage visibility. For manual direct entries, the lineage section must explicitly display "Direct Entry - No source trail".
- [FUNC-GMAIL-31] Pipeline Reversion & Raw Input Deletion: The user must be able to revert records to previous pipeline stages or delete raw inputs/direct ledger records exclusively through the details or correction modal. Reverting an email-source Gold record completely removes it from the Gold ledger and transitions its parent Silver record back to pending/error status. Reverting a Silver record completely removes it from Silver staging and marks the corresponding Bronze input as unprocessed. Active Bronze records (raw inputs) and direct manual Gold transactions can be soft-deleted. The system must prompt the user with a context-sensitive confirmation modal. Users can view soft-deleted records in a Trash Bin and restore them to their active states.
- [FUNC-GMAIL-32] Staging Validation & Error Status: Staging transactions (Silver layer) must be automatically validated after extraction. If a transaction lacks a merchant, transaction date, amount, or payment method, it must be flagged with an `error` status instead of `pending`, and highlighted as an error in the Silver staging table (with select checkboxes disabled to block batch approval). In the review modal, missing required fields must be highlighted, and the user must not be allowed to approve the transaction to the Gold ledger until all missing fields are corrected. Once corrected and saved as a draft, the transaction status must transition to `pending` (review state), enabling approval. Category is optional.
- [FUNC-GMAIL-33] Payment Standardization Config: The user must be able to manage a list of standardized payment methods (add, edit, delete) and alias mapping rules (e.g. mapping "hdfc" -> "HDFC Credit Card") in a dedicated "Payment Standardization" tab on the Data Ingestion page.
- [FUNC-GMAIL-34] Auto-Standardization on Extraction: During LLM extraction and manual entry ingestion, payment methods must be automatically normalized using the user's mapping rules before saving them to the Silver layer (or Gold layer for direct entry).
- [FUNC-GMAIL-35] Standardized Dropdown Selection: All UI forms that accept a payment method (Silver staging edits, Gold corrections, Direct manual entries) must render a dropdown selection populated from the user's standardized payment methods list rather than a free-text input field.
- [FUNC-GOLD-PAGE-1] Gold Transactions Page: The system must provide a dedicated Gold Transactions page accessible at the route `/transactions` that retrieves and displays all confirmed transaction records from the Gold medallion stage.
- [FUNC-GOLD-PAGE-2] Navigation: The user must be able to navigate to the Gold Transactions page through a link labeled "Transactions" in the primary navigation bar.
- [FUNC-GOLD-PAGE-3] High-Density Listing: The page must display a high-density table view listing the verified transaction fields from the Gold stage: Transaction Date, Merchant, Source Type, Inferred/Assigned Category, Payment Method, Amount, and Currency (excluding Notes to maximize layout density).
- [FUNC-GOLD-PAGE-4] Search and Date Filtering: The user must be able to search transactions by keyword (merchant, notes, payment method, category) and filter listed records dynamically by selecting a start and end date range.
- [FUNC-GOLD-PAGE-5] Sorting: The user must be able to sort the transactions dynamically by Date, Merchant name, and Amount.
- [FUNC-GOLD-PAGE-6] Total Sum Widget: The page must render a responsive totals summary widget showing sum totals of transactions grouped by currency.
- [FUNC-GOLD-PAGE-7] Ledger Corrections & Reversion: The user must be able to click on the Merchant field in the Gold Transactions table to open the details/corrections modal. Inside this modal, they must be able to modify transaction fields, soft-delete manual transactions, delete email-sourced records, or revert the transaction back to the Silver staging stage.
- [FUNC-GOLD-PAGE-8] Medallion Lineage Silver Staging View: In the Gold corrections/details modal, the detailed Silver pre-correction card and raw Bronze email body must be hidden by default and toggleable via a collapsible button. When expanded, the modal must display the original Silver staging card first (Merchant, Amount, Currency, Date, Category, Payment Method, and Transaction Type) followed by the raw Bronze email body below it, allowing the user to easily trace pre-correction logs.
- [FUNC-GMAIL-36] Staging Rejection: The user must be able to reject a staging transaction (Silver layer) from the detail view modal. Marking a transaction as rejected updates its status to `rejected` in the database, updates the visible staging list table row status badge to "Rejected" immediately, and excludes the record from both the "Pending" count in the Silver layer and the "Pending" staging metric card on the dashboard.
- [FUNC-GMAIL-37] Bronze Pipeline Statuses: Raw inputs (Bronze layer) must have three formal statuses: processed, unprocessed, and rejected. A user must be able to reject a raw input from the detail view modal. Rejecting a raw input updates its status to 'rejected' in the database, displays a 'Rejected' status badge, and excludes the email from the unprocessed select-all and batch extraction queue. The user can also restore a rejected raw input to unprocessed.
- [FUNC-GMAIL-38] Bronze Batch Rejection: The user must be able to select multiple unprocessed raw inputs in the Bronze table view and reject them in a single batch operation, updating their statuses to 'rejected' in the database and the UI instantly, excluding them from the unprocessed select-all and batch extraction queue.
- [FUNC-GMAIL-39] Refund Ingestion & Ledger Offsets: The system must automatically identify transaction refunds and credit reversals during ingestion/LLM extraction, mark their type as 'refund' in staging, support linking them to a parent purchase transaction, store them as positive offset-type entries in the database, display them as negative items in ledger tables, and deduct refund totals from category and net expenditure metrics across the app.
- [FUNC-GMAIL-40] LLM Extraction Log Persistence: During raw input detail extraction, the system must save an immutable snapshot of all LLM parsed values (merchant, amount_cents, currency, date, category, paymentMethod, transactionType, confidence_score) in the `llm_extraction_logs` table for future audit and accuracy verification.
- [FUNC-GOLD-PAGE-9] Lineage LLM Comparison View: In the Gold details/corrections modal, when the lineage trace is expanded, the system must retrieve the corresponding LLM log and display a side-by-side comparison table between the original LLM predictions and the finalized ledger values, highlighting user corrections.
- [FUNC-GOLD-PAGE-10] Dashboard LLM Accuracy Metrics Panel: The Dashboard page must render a responsive metrics card displaying the overall LLM accuracy rate and individual field-by-field accuracy rates (merchant, amount, category, payment method) based on matching counts between confirmed ledger entries and their original LLM logs.
- [FUNC-GMAIL-41] Staging LLM Extracted Data Preview: When reviewing a pending transaction in the Silver staging queue, the details modal must retrieve the corresponding LLM extraction log and display the original LLM extracted details (Merchant, Amount, Category, Payment Method) as a read-only preview card, helping the user compare the current editable fields with the original LLM output.
- [FUNC-GMAIL-42] Payment Mapping Priority Ranking: When matching a raw payment method string to standardized payment methods, the system must evaluate all matching mapping rules and prioritize the most specific rule. The specificity (rank) is calculated first by the number of parts (AND conditions) in the alias pattern (descending) and second by the total length of the alias pattern string (descending). The matching rule with the highest rank is applied.
- [FUNC-GMAIL-43] LLM Category Extraction Inference: During transaction extraction, the system must instruct the local LLM service to analyze the raw email content and infer a logical category for the transaction (e.g. Restaurant, Medical, Online Food Order, Transport, Shopping, Utilities, or Other) based on overall semantic context.
- [FUNC-GMAIL-44] Category Standardization & Normalization: When saving or updating categories (via LLM extraction, manual staging updates, or direct manual entries), the system must normalize the category string. The normalization trims leading/trailing spaces, maps case-insensitive matches to the standard predefined categories, and capitalizes custom user-defined categories (Title Case) to prevent duplicate names like "groceries" and "Groceries".
- [FUNC-GOLD-PAGE-11] Ledger Category, Method, and Source Filtering: On the Gold Transactions page (/transactions), the user must be able to filter transactions by Category, Payment Method, and Ingestion Source (Email Ingested vs. Manual Entry) via dropdown selectors in the filter panel, enabling instant view updates and recalculated total summaries.
- [FUNC-GMAIL-45] Currency Corrections in Modals: On both the Silver staging review modal and the Gold ledger corrections modal, the user must be presented with an input field to review and modify the transaction currency. Saving the changes must propagate the corrected currency code to the database layer and update corresponding total aggregates dynamically.
- [FUNC-GMAIL-46] Medallion Filtering Uniformity: The user must be able to filter and sort the transactions listed in the Silver staging queue and the Gold pipeline ledger view using keyword search, Sort By, and MultiSelect filters for Category, Payment Method, Ingestion Source, and Currency, providing absolute UI and filtering behavior consistency with the Ledger page.
- [FUNC-GMAIL-47] Dedicated Currency Column and Filter: A dedicated Currency column must be rendered in the tables of the Silver staging queue, Gold pipeline ledger view, and the main Ledger page, displaying the currency code separate from the Amount column. The user must be able to filter listed records dynamically by selecting one or more currency codes from a MultiSelect Currency dropdown filter.
- [FUNC-GMAIL-48] Reject Implies Non-Transactional Classification: When the user rejects a Bronze raw input (individually or in a batch), the system must atomically mark it as both rejected in status and non-transactional in classification. The user must see the rejected record immediately disappear from the Transactions sub-tab and appear in the Non-Transactional sub-tab, removing it from the extraction queue. This behaviour must persist across page reloads.
- [FUNC-GMAIL-49] Transfer (Own Account) Transaction Type: The user must be able to classify any staging or confirmed ledger transaction as a "Transfer (Own Account)" using a clearly labeled dropdown option. Transfers represent movements of money between the user's own accounts and must not be counted as expenditures. Transfers must be explicitly marked by the user — the system must never automatically classify a transaction as a transfer. When a transaction is classified as a transfer, its amount must be displayed in a distinct neutral color (indigo) in the Silver, Gold, and Transactions tables with no leading minus sign. The user must see a "Transfer" badge next to the merchant name in all affected table rows. Transfers must be completely excluded from all expense totals, dashboard metrics, currency aggregate summaries, and net expenditure calculations. The "Transfer (Own Account)" option must be available in all transaction type dropdowns, including the Silver staging review modal, Gold corrections modal, and the Direct Ledger Entry form.
- [FUNC-GMAIL-50] Timezone-Aware Ingestion Date and Time Rendering: The user must see the email received date and time displayed in their local timezone and formatted for their local region across all areas of the interface (including list tables, detail modal views, and Medallion pipeline lineage graphs).
- [FUNC-GMAIL-51] Persistent Fetcher Sender Emails: The user must be able to persist the sender email addresses they add or use for fetching emails in a database, associated with their user identity to enforce data isolation and avoid duplicate email storage per user. When the user wants to add or input sender email addresses in the fetcher config on the Data Ingestion page, they must be shown a list of previously added/saved sender emails as autocomplete suggestions (e.g. via a datalist or dropdown) from which they can select. If the user inputs a new sender email address and adds it to the fetcher configuration, the system must automatically save it to their persistent sender email list in the database if it doesn't already exist, ensuring no duplicates are stored.
- [FUNC-GMAIL-52] Dynamic Category Suggestions: All UI forms that accept a transaction category (including the Silver staging review/edit modal, Gold ledger corrections/details modal, and the Direct Ledger Entry/Fixed Charge creation forms) must display autocomplete suggestions (datalists) populated dynamically. The suggestion list must combine all predefined standard categories with all custom categories dynamically extracted from the user's existing Gold ledger and Silver staging transactions. The suggestion list must be deduplicated case-insensitively and sorted alphabetically.
- [FUNC-GOLD-PAGE-12] Collapsible Category Spend Breakdown Panel: The user must be able to make the "Category Spend Breakdown" panel visible or hide it via a checkbox control labeled "Show Category Breakdown" in the filter panel on the Ledger page. By default, this panel must be hidden. When visible, the panel must dynamically aggregate and show category-wise spend details for the currently filtered transactions (grouped by category and currency, accounting for refunds and excluding transfers). The user must be able to expand and collapse the panel, customize visible categories, and dismiss individual category spend cards. The checkbox state must not be reset when clicking the "Clear Filters" button.
- [FUNC-GOLD-PAGE-13] Clear Filters Option: The user must be able to reset all active search keywords, category selects, payment methods, ingestion sources, currency selects, transaction type selects, and date ranges in one click by using a "Clear Filters" button on the Gold Transactions page, instantly restoring the unfiltered list view and cumulative aggregates.
- [FUNC-GOLD-PAGE-14] Date Range Default Initialization: When the Ledger page loads, the date range filters must be automatically initialized. The start date filter must default to the active cycle's start date (sourced from the Cycle Engine), and the end date filter must default to the active cycle's dynamic end date (or current date). The user must be able to change these date filters manually and reset them using the Clear Filters button.
- [FUNC-GOLD-PAGE-18] Transaction Type Filtering & Keyword Search Support: The user must be able to filter transactions by transaction type (Expense, Refund, Transfer) using a dedicated MultiSelect filter labeled "Type:" on the Ledger page, as well as search for transaction types (e.g. typing "refund", "transfer", "expense") directly in the Keyword Search bar across Ledger and Pipeline tables.
- [FUNC-GOLD-PAGE-15] Real Data Cycle Trend Visualizer: The Dashboard page must render a billing cycle expense trend chart that displays the sum of actual expenditures (excluding transfers and fixed charges, and subtracting refunds) for each day. The chart must automatically calculate and display the daily totals for all days in the active billing cycle. Each bar on the chart must dynamically represent the spent amount with its corresponding day-of-week abbreviation label and date.
- [FUNC-GOLD-PAGE-16] Dashboard Layout Restructuring: The Dashboard page (/) must organize its components into two clear thematic sections under distinct visual headers: "Ledger Analytics & Financial Health" (containing the Salary Allocation Breakdown panel and the full-width Expense Trend visualizer) and "Ingestion Pipeline & Automation" (containing the Bronze card, the Silver card, and the Gold card arranged side-by-side in a 3-column row, with the LLM Parser Performance card rendered at the bottom).
- [FUNC-GOLD-PAGE-17] Filterable Cycle Expense Comparison Graph: The Dashboard page must render a "Cycle Comparison Trend" graph card in the "Ledger Analytics & Financial Health" section. The chart must display expenditure trends aligned by day of the billing cycle. The dropdown list of comparable historical cycles must be populated dynamically from user_cycles data output by the Cycle Engine, replacing fixed ±30-day offset math. The user must be able to select and toggle any cycle to overlay it on the Current Cycle line chart. The chart X-axis must normalize days based on each selected cycle's actual length. The user must see filter buttons/pills to select specific payment methods to filter chart data, toggle between "Daily Spend" and "Cumulative Spend" views, and hover over coordinates to view an interactive tooltip.

## Dynamic Cycle Management [FUNC-CYCLE]
- [FUNC-CYCLE-1] Dual Mode Cycle Start Configuration: The user must be able to set the start point of any billing cycle (active or historical) using either: (a) Transaction Anchor Mode — selecting a transaction from the Gold Ledger as a Start Anchor, using its exact Gmail timestamp (source_received_at) as the cycle start timestamp, or (b) Custom Date Mode — entering a custom start date (YYYY-MM-DD). By default, all cycles must fall back to the user's recurring start-day preference (default 17th of the month) with zero automated guesswork.
- [FUNC-CYCLE-2] Cycle History Manager & Dynamic Chaining: The user must see a Cycle History Manager table under the "Cycle & Salary Settings" tab (/ingestion), displaying all active and historical cycles, their anchor types (default, transaction, or date), start date/time, and options to set, edit, or reset overrides. Setting or updating a cycle's start point must automatically update the end boundary of the preceding cycle to end one millisecond before the new cycle's start timestamp.
- [FUNC-CYCLE-3] Same-Day Intra-Day Boundary Ordering: When filtering transactions for a cycle, transactions occurring on a boundary date must be evaluated using their full source_received_at timestamp (or createdAt timestamp fallback). Transactions occurring before a cycle's start timestamp must remain in the preceding cycle, while transactions occurring on or after the start timestamp must belong to the new cycle.
- [FUNC-CYCLE-4] Anchor Deletion Guard: If a user attempts to delete a Gold Ledger transaction that is currently set as a cycle start anchor, the system must display a warning notification informing the user that the transaction is an anchor, offering to reset that cycle to the default start-day rule before proceeding with deletion.
- [FUNC-CYCLE-5] Unified Cycle Picker Dropdown: The user must be able to select any active or historical billing cycle from a standardized Cycle Selector dropdown on the Dashboard (/), Gold Ledger (/transactions), Financial Analytics (/analytics), and Financial Insights (/insights) pages. Selecting a cycle must instantly update all spend breakdowns, charts, run-rate forecasts, and table filters to match that cycle's exact date range and timestamps.

## Financial Analysis [FUNC-ANALYSIS]
- [FUNC-ANALYSIS-1] User Settings Configuration: The user must be able to configure their monthly budget parameters, specifically "Billing Cycle Start Day" (restricted to integers 1-28, default 17) and "Expected Monthly Salary" (positive number, default 100000) inside a dedicated "Cycle & Salary Settings" tab on the Data Ingestion control page (/ingestion). The user must also view and manage their full historical cycle list in the Cycle History Manager table within the same tab.
- [FUNC-ANALYSIS-2] Cashflow and Budget Allocation Visualization: The user must see a visual breakdown of their salary allocation split into three buckets ("Invested Wealth", "Consumption Expenses", and "Unspent (Liquid Savings)") rendered as a segmented progress bar with a detailed currency legend. This Allocation panel must be positioned on the Dashboard page (/) above the weekly trend visualizer card.
- [FUNC-ANALYSIS-3] Dynamic Billing Cycle Integration: The active cycle range is computed dynamically by the Cycle Engine based on user cycle overrides and the default Billing Cycle Start Day configuration. The visual budget allocation bar on the Dashboard page must strictly compute transaction balances within this active billing cycle range.
- [FUNC-ANALYSIS-4] Daily Spend Timeline on Ledger Page: The user must be able to make the "Daily Spend Timeline" panel visible or hide it via a checkbox control labeled "Show Daily Spend Timeline" in the filter panel on the Ledger page. By default, this panel must be hidden. When visible, the user must see an interactive visual timeline representing daily spending rendered as a lightweight SVG line/area chart (with explicit X and Y axes, coordinate dots, tooltips, ticks, and values/date labels), dynamically updating in synchronization with other active search/filter controls. The user must also be able to toggle average/trend lines in the panel header. The checkbox state must not be reset when clicking the "Clear Filters" button.
- [FUNC-ANALYSIS-5] Recurring Fixed Charges Config: The user must be able to configure and manage recurring fixed charges (such as EMI, house rent) under the "Cycle & Salary Settings" tab on the Data Ingestion control page (/ingestion). For each fixed charge, the user must specify a Description/Name, Amount, Currency, Category, Payment Method, Start Date (YYYY-MM-DD), and End Date (YYYY-MM-DD) as mandatory fields. The user must be able to see a list of their saved fixed charges and delete any entry.
- [FUNC-ANALYSIS-6] Upfront Ledger Generation for Fixed Charges: When the user saves a fixed charge template, the system must automatically calculate all monthly cycles between the start date and the end date (inclusive, on the same day of the month as the start date) and insert a transaction row for each occurrence in the Gold Ledger (gold_transactions) table with transaction type set to "Fixed Charge" ('fixed') and notes containing the trace tag "Fixed Charge ID: [id] | Auto-generated".
- [FUNC-ANALYSIS-7] Future Occurrence Syncing on Edit/Delete: When the user edits an existing fixed charge settings template, the system must update all future occurrences (where transaction date is on or after today) in the Gold Ledger to match the new name, amount, category, or end date, while leaving past occurrences (before today) untouched for historical record integrity. When the user deletes a template, all associated future transactions must be deleted from the ledger.
- [FUNC-ANALYSIS-8] Fixed Charge Type and Allocation Exclusion: The user must be able to classify any transaction as "Fixed Charge" ('fixed') using a clearly labeled dropdown option in all transaction type select controls. Transactions of type "Fixed Charge" must be completely excluded from standard discretionary consumption expenses, net aggregates, and transaction totals to prevent double-counting, returning a signed amount of 0 in aggregates.
- [FUNC-ANALYSIS-9] Salary Allocation Itemized Fixed Charges: The user must see the list of active fixed charges and their combined amounts displayed inside the "Salary Allocation Breakdown" card on the Dashboard page (/), showing how they are incorporated.
- [FUNC-GMAIL-53] Header-based Bulk Action Dropdown & Batch Editing: The user must be able to select multiple transactions via checkboxes in the Silver staging queue, Gold pipeline view, and Gold Ledger Transactions page. Upon selecting one or more items, the table column headers must dynamically transition to show the selection count and a "Bulk Actions" dropdown menu button. Selecting "Batch Edit" from this menu must open a Batch Edit Modal showing inputs (Merchant, Amount, Category, Date, Payment Method, Type, Notes) with field-level toggle switches. ## LLM Feedback Learning [FUNC-FEEDBACK]
- [FUNC-FEEDBACK-1] Correction-Driven Extraction Learning: When the LLM Feedback Learning feature is enabled, the system must automatically capture manual user corrections made to LLM-extracted fields (merchant, category, payment method, or transaction type) at any pipeline stage — Silver draft save, Silver approval, or Gold ledger correction. The system must ignore auto-applied category or payment rules when the user accepts them without changes, ensuring only manual user overrides are learned. To maximize prompt context efficiency, the user must experience semantic few-shot prompt enrichment where the system dynamically identifies and injects only the most semantically relevant past corrections for the current raw email being extracted, filtering out unrelated examples based on a configurable similarity threshold, and falling back to a recency-based injection list if the semantic similarity engine is offline.
- [FUNC-FEEDBACK-2] Feedback Feature Toggle: The user must be able to enable or disable the LLM Feedback Learning feature from a dedicated "LLM Feedback Learning" tab on the Data Ingestion page. When disabled, the system must capture zero corrections and inject zero examples into extraction prompts, leaving the extraction pipeline completely unchanged.
- [FUNC-FEEDBACK-3] Configurable Example Count: The user must be able to configure the maximum number of correction examples (between 1 and 50) that are injected into the LLM prompt at extraction time. The system must default to 10 examples when no preference has been set.
- [FUNC-FEEDBACK-4] Correction Example Visibility and Management: The user must be able to view all stored correction examples in a paginated table on the LLM Feedback Learning tab, showing field name, original LLM value, corrected value, email context snippet, and date. The user must be able to delete individual examples or clear all examples in one operation from the same tab.
